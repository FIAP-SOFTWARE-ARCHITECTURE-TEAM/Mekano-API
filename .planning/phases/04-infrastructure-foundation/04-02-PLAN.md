    # INF-02: Manifestos Kubernetes para Mekano

    **Responsável:** Elias
    **Prioridade:** Alta
    **Dependências:** Nenhuma (Kind local não precisa de cloud)

    ## Objetivo

    Criar manifestos K8s no diretório `k8s/` para deploy do Mekano em cluster **Kind** local.

    ## Contexto

    O Mekano é uma API Quarkus com PostgreSQL 16. O docker-compose existente (referência para env vars e healthchecks) define o comportamento esperado: healthcheck via `/q/health/live`, JWT Ed25519 via volume de segredos, variáveis de ambiente para DB e JWT.

    O cluster Kind **não vem com metrics-server** — necessário instalar para HPA funcionar ([kind.sigs.k8s.io](https://kind.sigs.k8s.io/docs/user/quick-start/)). O HPA pode ser testado com `kubectl run -i --tty --image=busybox` gerando carga.

    ## Manifestos a criar

    | Arquivo | Recurso | Detalhes |
    |---------|---------|----------|
    | `k8s/namespace.yaml` | Namespace | `mekano` |
    | `k8s/configmap.yaml` | ConfigMap | `QUARKUS_PROFILE=prod`, issuer config |
    | `k8s/secret.yaml` | Secret | `DB_USER`, `DB_PASSWORD`, `privateKey.pem` (Ed25519 PEM) |
    | `k8s/deployment.yaml` | Deployment | 2 réplicas, resource limits, liveness/readiness probes (`/q/health/live`, `/q/health/ready`) |
    | `k8s/service.yaml` | Service | ClusterIP porta 8080 |
    | `k8s/hpa.yaml` | HPA | CPU 70%, min 2, max 6 réplicas |
    | `k8s/ingress.yaml` | Ingress | Opcional — Elias decide se necessário |

    ## Probes (referência do docker-compose)

    ```yaml
    livenessProbe:
      httpGet:
        path: /q/health/live
        port: 8080
      initialDelaySeconds: 30
      periodSeconds: 10
    readinessProbe:
      httpGet:
        path: /q/health/ready
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 5
    ```

    ## Variáveis de ambiente (referência do compose)

    | Variável | Valor (Kind) | Origem |
    |----------|-------------|--------|
    | `QUARKUS_PROFILE` | `prod` | ConfigMap |
    | `DB_URL` | `jdbc:postgresql://postgres:5432/mekano` | ConfigMap |
    | `DB_USER` | `mekano` | Secret |
    | `DB_PASSWORD` | (definir) | Secret |
    | `SMALLRYE_JWT_SIGN_KEY_LOCATION` | `/etc/mekano/secrets/privatekey.pem` | Secret (volume mount) |
    | `MP_JWT_VERIFY_PUBLICKEY_LOCATION` | `/etc/mekano/secrets/publicKey.pem` | ConfigMap (chave pública) |

    ## Decisões que Elias precisa tomar

    - Localização das chaves JWT dentro do pod (/etc/mekano/secrets/ ou /home/jboss/.mekano/secrets/)
    - Ingress: necessário? Se sim, qual controller (nginx-ingress, Traefik)?
    - Resource limits/requests para CPU e memória

    ## Acceptance Criteria

    1. `kind create cluster` + `kubectl apply -f k8s/` aplica todos os manifests sem erro
    2. Pods do Mekano iniciam e passam liveness/readiness probes
    3. Service ClusterIP expõe a API internamente no namespace `mekano`
    4. HPA escala de 2 para N pods quando CPU > 70% (requer metrics-server instalado)
    5. `kubectl port-forward svc/mekano-service 8080:8080 -n mekano` + `curl http://localhost:8080/q/health/live` retorna 200
    ```

    # INF-03: Scripts Terraform para Provisionamento (EKS + RDS)

    **Responsável:** Elias
    **Prioridade:** Alta
    **Dependências:** Conta AWS com permissões para EKS, RDS, S3, DynamoDB

    ## Objetivo

    Criar scripts Terraform em `terraform/` para provisionar cluster EKS e RDS PostgreSQL.

    ## Contexto

    O Mekano usa PostgreSQL 16 e roda em containers. Em produção, o banco será RDS gerenciado e a aplicação no EKS. **S3 backend + DynamoDB state locking desde o primeiro `terraform init`** (prevenir perda/corrupção de estado).

    ## Estrutura esperada

    | Arquivo | Conteúdo |
    |---------|----------|
    | `terraform/main.tf` | Provider AWS, módulo VPC, EKS cluster, node group |
    | `terraform/rds.tf` | RDS PostgreSQL 16, subnet group, security group |
    | `terraform/backend.tf` | S3 bucket backend + DynamoDB state locking |
    | `terraform/variables.tf` | Region, environment, instance types |
    | `terraform/outputs.tf` | Cluster endpoint, RDS endpoint |
    | `terraform/versions.tf` | Terraform >= 1.5, AWS provider version pinned |

    ## Regras importantes

    - `.gitignore` deve excluir `*.tfstate`, `*.tfstate.*`, `.terraform/`
    - Backend S3 com `use_lockfile = true` ou DynamoDB
    - RDS em subnet privada, acessível apenas do EKS
    - Security group do RDS permite tráfego apenas do security group do EKS

    ## Decisões que Elias precisa tomar

    - Região AWS (us-east-1? sa-east-1?)
    - Instance types (t3.medium para node group?)
    - RDS instance class (db.t3.small?)
    - Nome do S3 bucket (único global)
    - Número de nodes (mín/máx do node group)

    ## Acceptance Criteria

    1. `terraform init` configura S3 backend + DynamoDB locking
    2. `terraform plan` mostra recursos a criar (VPC, EKS, RDS, S3, DynamoDB)
    3. `terraform apply` provisiona cluster EKS acessível via `kubectl`
    4. RDS PostgreSQL 16 acessível a partir dos pods no EKS
    5. State remoto no S3, protegido por DynamoDB lock
    6. `terraform destroy` limpa todos os recursos sem dangling
    ```

    # INF-04: Pipeline de CD no GitHub Actions

    **Prioridade:** Alta
    **Dependências:** INF-02 (K8s manifests), INF-03 (Terraform — cluster EKS provisionado)

    ## Objetivo

    Adicionar pipeline de CD ao repositório Mekano para build automático e deploy no cluster EKS.

    ## Pipeline esperada

    **Trigger:** push na branch `main` (após CI passar)

    **Steps:**
    1. **Build JAR:** `mvn -B -ntp package -pl mekano-rest -am -DskipTests`
    2. **Build Docker image:** `docker build -f mekano-rest/src/main/docker/Dockerfile.jvm -t <registry>/mekano-api:<tag> .`
    3. **Push to registry:** GHCR ou Docker Hub
    4. **Deploy to K8s:**

       - Opção B: `kubectl apply -f k8s/` (se usar imagem tag `latest`)

    - Deploy automático vs semi-automático (approval gate)?
    - Nome do workflow: adicionar job no `ci.yml` ou criar `cd.yml` separado?

    ## Acceptance Criteria

    1. Push para `main` dispara pipeline automaticamente
    2. Imagem Docker é buildada e publicada no registry
    3. Deploy no cluster EKS é executado (automático ou com aprovação manual)
    4. Rollback possível revertendo o commit e fazendo novo push
    5. Pipeline falha se build falhar ou imagem não for publicada
