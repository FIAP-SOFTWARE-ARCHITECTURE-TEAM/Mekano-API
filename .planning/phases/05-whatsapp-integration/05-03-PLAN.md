    This document formally addresses API-05: "Verificar escopo de atualização de status via ferramenta externa (WhatsApp/e-mail) — aplicar somente a aprovar/recusar orçamento?"

    Structure the document with these sections:

    ### 1. Requirement Reference
    - **API-05** from REQUIREMENTS.md: full verbatim text
    - Phase 5 placement rationale

    ### 2. Scope Definition (the core answer)
    **Answer:** Yes — apply ONLY to approve/reject orçamento.

    Document the precise scope:
    - **Approved:** Aprovar orçamento (OS: AGUARDANDO_APROVACAO → AGUARDANDO_EXECUCAO)
    - **Approved:** Reprovar orçamento (OS: AGUARDANDO_APROVACAO → CANCELADA)
    - **Not approved:** All other status transitions (iniciar diagnóstico, iniciar execução, finalizar execução, gerar cobrança, confirmar pagamento, entregar, cancelar)
    - **Not approved:** Any DB write operations (CRUD on clientes, veículos, peças, etc.)
    - **Not approved:** Any read operations beyond what the existing @PermitAll endpoints expose

    ### 3. Rationale
    Why only approve/reject orçamento via external channel:
    1. **Security (per ASVS V4 Access Control):** Approve/reject orçamento are the only transitions with @PermitAll on the existing API (OrcamentoResource.java lines 66-92). The external channel maps to the same permission boundary.
    2. **Existing public endpoints:** `POST /orcamentos/{uuid}/aprovar` and `/reprovar` already exist as `@PermitAll` — WhatsApp reuses the same authorization model (orcamento ownership by UUID).
    3. **One-time decision:** Orçamento approval/rejection is a single, high-stakes binary decision. Other transitions require professional judgment (mecânico inicia diagnóstico, execução) or authenticated roles (admin registra entrega).
    4. **D-12 explicit decision:** Context.md D-12: "Cliente pode aprovar/recusar orçamento via WhatsApp (webhook processa resposta e chama endpoint de aprovação interno). WhatsApp não substitui a API pública — é um canal adicional."
    5. **Simplicity:** Adding more interactive flows would require richer WhatsApp conversation state management and template approval, which is deferred (per RESEARCH.md §Deferred Ideas).

    ### 4. Architecture Flow (Mermaid diagram)
    ```mermaid
    sequenceDiagram
        participant C as WhatsApp Client
        participant EA as Evolution API
        participant MW as Mekano Webhook
        participant OS as OrcamentoService
        participant DB as Database

        C->>EA: Clica "✅ Aprovar"
        EA->>MW: POST /api/v1/webhooks/whatsapp<br/>apikey + selectedButtonId
        MW->>MW: Validate apikey header
        alt Invalid apikey
            MW-->>EA: 401 Unauthorized
            EA-->>C: Error message
        else Valid apikey
            MW->>OS: aprovar(AprovarOrcamentoCommand)
            OS->>DB: @Transactional: update OS status
            DB-->>OS: OK
            OS-->>MW: Orcamento aprovado
            MW-->>EA: 200 OK
            EA-->>C: "✅ Orçamento aprovado!"
        end
    ```

    ### 5. Security Boundary
    - **Access control:** WhatsApp is an additional channel for the SAME @PermitAll operation. Users still need to know the orcamento UUID (which is scoped to their OS).
    - **Authentication:** Webhook validates apikey header → 401 if invalid. The orçamento approve/reject uses UUID-based ownership (existing).
    - **Rate limiting:** The ORIGINAL API has rate limiting (if any). WhatsApp webhook goes through the same OrcamentoService — rate limiting applies transitively. If the API has no rate limiting, both channels share that status.
    - **Audit log:** All approve/reject operations are logged via the existing OsAuditLog mechanism (OS status transitions are already audited).

    ### 6. Implementation Verification Checklist
    Checkbox table verifying each component exists:
    - [x] WhatsAppNotifierPort — domain port (05-01)

    - [x] WhatsAppPagamentoObserver — trigger on PagamentoConfirmadoEvent (05-02)
    - [x] WhatsAppWebhookResource — POST /api/v1/webhooks/whatsapp (05-02)
    - [x] WhatsAppWebhookService — processes button replies (05-02)
    - [x] Webhook validates apikey → 401 on invalid (05-02)
    - [x] processButtonReply has @Transactional (05-02)
    - [x] Button ID format: `"approve_orc_<uuid>"` and `"reject_orc_<uuid>"` (05-01, 05-02)

    Use actual file paths and line numbers for each checkbox.

    ### 7. Boundary Decisions
    Document what is intentionally OUT of scope (with reasoning):
    - **Email as external channel:** Not implemented. WhatsApp was chosen as the single external channel per D-01. Email notification would require a separate integration.
    - **Other status transitions via WhatsApp:** Not implemented per scope definition above. Future phases MAY add more interactive flows if WhatsApp two-way conversation support is needed.
    - **Multi-language support:** Not in scope. Messages are in Brazilian Portuguese only.
    - **Payment confirmation via WhatsApp:** Deferred (STATE.md §Deferred Items — payment gateway real integration is v2.x).
