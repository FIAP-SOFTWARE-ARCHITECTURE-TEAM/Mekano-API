# Phase 1: Auth & OS Foundation — Research

**Researched:** 2026-06-22
**Domain:** JWT Authentication, Role-Based Access Control, CRUD Aggregates, Order-of-Service State Machine
**Confidence:** HIGH

## Summary

Phase 1 builds the entire authentication layer from scratch (JWT Ed25519/EdDSA with refresh token rotation) plus four new aggregates (Cliente, Veiculo, Servico, OrdemDeServico) following the established User pattern. The architecture is Clean Architecture with 4 Maven modules, 5 developers working in parallel via vertical slices per entity.

The key technical decisions are: SmallRye JWT Build API for token generation (`Jwt.claims().sign()`), EdDSA/Ed25519 via `mp.jwt.verify.publickey.algorithm=EdDSA`, Flyway V6-V10 using H2-compatible SQL (`BIGINT GENERATED BY DEFAULT AS IDENTITY`), and a state machine for OS transitions using `Map<StatusOS, Set<StatusOS>>` as single source of truth with explicit transition methods (no `setStatus()`). The `user_roles` N:N table enables future multi-role support.

**Primary recommendation:** Follow the exact User pattern for all 4 new aggregates. Auth is built from scratch — not reused. All 5 devs work in parallel: Dev1 Auth, Dev2 Cliente, Dev3 Veiculo, Dev4 Servico, Dev5 OS.

## User Constraints (from CONTEXT.md)

### Locked Decisions

#### Autenticação JWT
- **D-01:** Algoritmo Ed25519/EdDSA. Claim `groups` com role único (usuário tem 1 role no JWT)
- **D-02:** Access token: 15 minutos de expiração
- **D-03:** Refresh token na Fase 1 com rotação automática (cada uso gera novo par, invalida anterior). Tabela `refresh_tokens` já existe (V2 migration)
- **D-04:** Chaves Ed25519 geradas via script no build (automático). Public key em `mekano-rest/src/main/resources/publicKey.pem`, private key em `~/.mekano/secrets/privatekey.pem`
- **D-05:** Só admin cria usuários do sistema (endpoint `POST /api/v1/users` protegido com `@RolesAllowed("admin")`)
- **D-06:** JWT contém claims: `sub` (UUID), `groups` (role), `name` (nome do usuário)
- **D-07:** Issuer: `https://mekano.fiap.com.br/auth` configurado via `MP_JWT_ISSUER` env var
- **D-08:** Login identifier: email + senha (POST /api/v1/auth/login)
- **D-09:** Endpoint `POST /api/v1/auth/logout` invalida refresh token no servidor

#### Roles e Permissões
- **D-10:** Tabela separada `user_roles` (N:N) — suporta múltiplos papéis por usuário no futuro. Na prática, cada usuário tem 1 role por enquanto
- **D-11:** Clientes CRUD: admin + atendente
- **D-12:** Veículos CRUD: admin + atendente
- **D-13:** Serviços (tipos de serviço) CRUD: só admin
- **D-14:** OS listar: todos os perfis; criar: admin + atendente
- **D-15:** Iniciar diagnóstico (RECEBIDA → EM_DIAGNOSTICO): mecânico + admin
- **D-16:** Endpoint público OS status: `@PermitAll` (sem autenticação)

#### Modelo do Cliente
- **D-17:** Só CPF (pessoa física) na Fase 1. CNPJ (pessoa jurídica) na Fase 2
- **D-18:** Value Object `Cpf` no domain — valida dígitos verificadores no construtor (padrão `Email` VO)
- **D-19:** Campos obrigatórios: nome, CPF, email, telefone
- **D-20:** Endereço completo: logradouro, número, bairro, cidade, UF, CEP (modelado como Value Object `Endereco`)
- **D-21:** Cliente pode ter múltiplos veículos (relacionamento 1:N)

#### Veículo
- **D-22:** Placa armazenada normalizada: uppercase, sem hífen. Ex: `ABC1234` ou `ABC1D23`
- **D-23:** Validação via regex único que cobre ambos os formatos (Mercosul + antigo). Identificação automática do formato — sem campo `tipo`
- **D-24:** Placa única no sistema (UNIQUE constraint no banco)

#### Ordem de Serviço e Máquina de Estados
- **D-25:** Matriz de transição completa (todos os estados do ciclo de vida) implementada desde a Fase 1. `Map<StatusOS, Set<StatusOS>>` como fonte única da verdade. Teste parametrizado cobrindo todas as transições
- **D-26:** Transição via métodos explícitos (ex: `os.iniciarDiagnostico()`) — NUNCA setter genérico `setStatus()` (previne Pitfall 5: lost updates)
- **D-27:** OS criada já com serviços solicitados (atendente informa no momento da criação)
- **D-28:** Itens da OS modelados como duas entidades separadas: `ServicoExecutado` + `PecaUsada`

#### Divisão do Trabalho (5 devs, dias 1-4)
- **D-29:** Divisão vertical por entidade: cada dev implementa uma entidade completa (domain → infra → rest). Dev1: Auth, Dev2: Cliente, Dev3: Veículo, Dev4: Serviço, Dev5: OrdemDeServico
- **D-30:** Ordem de implementação: entidades primeiro (Cliente, Veículo, Serviço, OS domain/infra/rest), auth depois (login + JWT + roles)

#### Dependências Maven a Adicionar
- `quarkus-smallrye-jwt` em `mekano-rest/pom.xml` — verificação JWT
- `quarkus-smallrye-jwt-build` em `mekano-rest/pom.xml` — geração JWT

- Detalhes de implementação não cobertos acima ficam a critério do agente/planner, respeitando os padrões existentes no codebase
- Estrutura exata dos testes e cobertura segue padrão já estabelecido (JUnit 5 + Mockito + REST Assured + AssertJ)

### Deferred Ideas (OUT OF SCOPE)
- **CNPJ (pessoa jurídica)**: Modelagem de cliente PJ com CNPJ fica para Fase 2. A estrutura atual (CPF-only) deve ser desenhada para permitir extensão futura
- **Refresh token pode virar feature opcional em versões futuras** se o modelo de segurança evoluir

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| JWT generation | Application | Infrastructure | Application orquestra login. Infrastructure carrega chave privada e invoca SmallRye JWT Build API. |
| JWT verification | Framework (REST) | — | Quarkus security filter via `mp.jwt.*` config. `@RolesAllowed` no resource. |
| Password verification | Application | Infrastructure | Service chama `PasswordHasher.matches()`. `BcryptPasswordHasher` no infrastructure. |
| Refresh token rotation | Application | Infrastructure | Service coordena: valida token antigo → gera novo par → persiste. `@Lock(PESSIMISTIC_WRITE)` no repository. |
| Cliente CRUD | REST | Application | Commands via service layer. Reads direto do repository (D-06 pattern). |
| Cliente/Veículo validação | Domain | — | Value Objects Cpf, PlacaVeiculo, Telefone, Endereco validam no construtor. |
| Veiculo CRUD | REST | Application | Same pattern as Cliente. |
| Servico CRUD | REST | Application | Admin-only `@RolesAllowed("admin")`. |
| OS state machine | Domain | — | `Map<StatusOS, Set<StatusOS>>` no domain entity. Métodos explícitos de transição. |
| OS persistence | Infrastructure | — | Two-class repository pattern com HQL + `@Version` para optimistic locking. |
| Public OS status | REST (PermitAll) | — | `@PermitAll` resource method. Only status + timestamps exposed. |

### Pattern 1: Domain Entity Pattern (follow User.java)
**What:** Pure POJO with private builder, factory methods `create()` and `reconstitute()`, no framework annotations.
**When to use:** Every new aggregate entity.
**Example:**
```java
@Getter
@Builder(access = AccessLevel.PRIVATE)
@ToString
public class Cliente {
    private final UUID id;
    private final String nome;
    private final Cpf cpf;
    private final Email email;
    private final Telefone telefone;
    private final Endereco endereco;
    private final LocalDateTime createdAt;

    public static Cliente create(String nome, String cpfValue, String emailValue,
                                  String telefoneValue, Endereco endereco) {
        return Cliente.builder()
                .id(UUID.randomUUID())
                .nome(nome)
                .cpf(new Cpf(cpfValue))
                .email(new Email(emailValue))
                .telefone(new Telefone(telefoneValue))
                .endereco(endereco)
                .createdAt(LocalDateTime.now())
                .build();
    }

    public static Cliente reconstitute(UUID id, String nome, String cpfValue,
                                        String emailValue, String telefoneValue,
                                        Endereco endereco, LocalDateTime createdAt) {
        // same but preserve id and createdAt
    }
}
```

### Pattern 2: OS State Machine Pattern
**What:** `Map<StatusOS, Set<StatusOS>>` as single source of truth with explicit transition methods. No `setStatus()`.
**When to use:** Only for OrdemDeServico entity.
**Example:**
```java
public enum StatusOS {
    RECEBIDA, EM_DIAGNOSTICO, AGUARDANDO_APROVACAO, EM_EXECUCAO, FINALIZADA, ENTREGUE, CANCELADA;

    private static final Map<StatusOS, Set<StatusOS>> TRANSICOES = Map.of(
        RECEBIDA, Set.of(EM_DIAGNOSTICO, CANCELADA),
        EM_DIAGNOSTICO, Set.of(AGUARDANDO_APROVACAO, CANCELADA),
        AGUARDANDO_APROVACAO, Set.of(EM_EXECUCAO, CANCELADA),
        EM_EXECUCAO, Set.of(FINALIZADA, CANCELADA),
        FINALIZADA, Set.of(ENTREGUE),
        ENTREGUE, Set.of(),
        CANCELADA, Set.of()
    );

    public boolean podeTransitarPara(StatusOS destino) {
        return TRANSICOES.get(this).contains(destino);
    }

    public void validarTransicao(StatusOS destino) {
        if (!podeTransitarPara(destino)) {
            throw new AppException(400, "Transição inválida: " + this + " → " + destino);
        }
    }

    public static Set<StatusOS> transicoesValidas(StatusOS origem) {
        return TRANSICOES.getOrDefault(origem, Set.of());
    }
}
```

### Pattern 3: Two-Class Repository Pattern
**What:** `PanacheRepository` (extension) + `RepositoryImpl` (port implementation) to avoid signature conflicts.
**When to use:** Every new aggregate.
**Example (from existing UserRepositoryImpl):**
```java
@ApplicationScoped
public class ClienteRepositoryImpl implements ClienteRepositoryPort {
    @Inject ClientePanacheRepository panacheRepository;
    @Inject ClienteEntityMapper mapper;

    @Override
    @Retry(maxRetries = 3)
    @CacheResult(cacheName = CacheNames.CLIENTES)
    public Optional<Cliente> findById(UUID id) {
        return panacheRepository.find("uuid = ?1 AND isActive = ?2", id, true)
                .firstResultOptional().map(mapper::toDomain);
    }

    @Override
    @Timeout(value = 5, unit = ChronoUnit.SECONDS)
    @CacheInvalidate(cacheName = CacheNames.CLIENTES)
    public Cliente save(Cliente cliente) {
        var entity = mapper.toEntity(cliente);
        panacheRepository.persist(entity);
        panacheRepository.flush();
        return mapper.toDomain(entity);
    }
}
```

### Pattern 4: JWT Token Generation (AuthResource)
**What:** SmallRye JWT Build API via `Jwt.claims(...).sign()` with EdDSA/Ed25519.
**Example:**
```java
import io.smallrye.jwt.build.Jwt;
import io.smallrye.jwt.SignatureAlgorithm;

// Access token (15 min)
String accessToken = Jwt.issuer("https://mekano.fiap.com.br/auth")
    .subject(user.getId().toString())           // sub = UUID
    .upn(user.getName())                        // name
    .groups(Set.of(role))                       // groups = single role
    .expiresIn(Duration.ofMinutes(15))
    .sign();

// Refresh token (7 days, opaque — store hash in DB)
String refreshToken = Jwt.claims()
    .claim("jti", UUID.randomUUID().toString())
    .claim("sub", user.getId().toString())
    .expiresIn(Duration.ofDays(7))
    .sign();
```

### Pattern 5: AuthResource Pattern
**What:** `@PermitAll` resource for login/refresh/logout, `@RequestScoped` for JWT claim injection.
**Example:**

```java
    @POST
    @Path("/logout")
    @Consumes(MediaType.APPLICATION_JSON)
    @Produces(MediaType.APPLICATION_JSON)
```

### Anti-Patterns to Avoid
- **`setStatus()` on OS:** Produces lost updates — use explicit transition methods (`iniciarDiagnostico()`, `aprovarOrcamento()`, etc.)
- **`@ApplicationScoped` on resources with JWT:** Breaks claim injection — always use `@RequestScoped` (G8)
- **`quarkus.smallrye-jwt.*` namespace:** Causes silent 401 — always use `mp.jwt.*` (G6)
- **MapStruct `componentModel = "spring"`:** NPE at runtime — always `"cdi"` (G9)
- **`@Transactional` on repository layer:** Prevents service-level transaction coordination (D-01)
- **`BIGSERIAL` in Flyway migrations:** Breaks H2 compatibility in tests — use `BIGINT GENERATED BY DEFAULT AS IDENTITY`

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| JWT generation | Manual JWT encoding (base64, header, signature) | SmallRye JWT Build API (`Jwt.claims().sign()`) | 6 edge cases: algorithm negotiation, key selection, claim validation, expiry, jti uniqueness, standard claims auto-fill |
| JWT verification | Manual public key loading + signature check | Quarkus SmallRye JWT (`mp.jwt.*` config) | Framework handles: key format detection (PEM/JWK/JWKS), algorithm negotiation, clock skew, issuer validation |
| Password hashing | Custom hash algorithm | BCrypt via `BcryptUtil` (existing) | Salt generation, constant-time comparison, hash upgrade path |
| State machine transitions | If/else-if chains | `Map<StatusOS, Set<StatusOS>>` matrix | Single source of truth; testable as data; prevents missing transitions |
| Repository boilerplate | Raw EntityManager queries | Panache HQL (`find("field = ?1", value)`) | Soft-delete filter, pagination, sort built-in |
| DTO mapping | Manual get/set calls | MapStruct `componentModel = "cdi"` | Field-mismatch detection at compile time; VO flatten expressions |
| Rate limiting | Thread.sleep counters | `TokenBucketRateLimiter` (existing) | Existing, tested, configurable |
| Error response format | Custom JSON error body | `ApiExceptionMapper` (existing) RFC 7807 | Already deployed, tested, handles `AppException` → Problem+JSON |

**Key insight:** Every custom solution in this domain introduces subtle bugs missed in review — JWT parsing has algorithm confusion vulnerabilities, password hashing has timing attacks, state machines have missing transitions. The standard library solutions have been hardened by thousands of production deployments.

## Value Objects Implementation Guide

### Cpf
```java
public final class Cpf {
    private static final Pattern CPF_PATTERN = Pattern.compile("\\d{11}");
    private final String value;

    public Cpf(String value) {
        if (value == null || value.isBlank()) {
            throw new AppException(400, "CPF é obrigatório");
        }
        String digits = value.replaceAll("\\D", "");
        if (!CPF_PATTERN.matcher(digits).matches()) {
            throw new AppException(400, "CPF deve conter 11 dígitos");
        }
        if (!validarDigitosVerificadores(digits)) {
            throw new AppException(400, "CPF inválido — dígitos verificadores não conferem");
        }
        this.value = digits;
    }

    private static boolean validarDigitosVerificadores(String cpf) {
        // Calculate 1st verifier digit
        int sum = 0;
        for (int i = 0; i < 9; i++) sum += (cpf.charAt(i) - '0') * (10 - i);
        int dig1 = 11 - (sum % 11);
        if (dig1 > 9) dig1 = 0;
        // Calculate 2nd verifier digit
        sum = 0;
        for (int i = 0; i < 10; i++) sum += (cpf.charAt(i) - '0') * (11 - i);
        int dig2 = 11 - (sum % 11);
        if (dig2 > 9) dig2 = 0;
        return dig1 == (cpf.charAt(9) - '0') && dig2 == (cpf.charAt(10) - '0');
    }
}
```

```java
@ApplicationScoped
public class AuthService implements AuthServicePort {
    private final UserRepositoryPort userRepository;
    private final RefreshTokenRepositoryPort refreshTokenRepository;
    private final PasswordHasher passwordHasher;

    public TokenPair login(String email, String password) {
        var user = userRepository.findByEmail(email)
            .orElseThrow(() -> new AppException(401, "Credenciais inválidas"));

        if (!passwordHasher.matches(password, user.getPasswordHash())) {
            throw new AppException(401, "Credenciais inválidas");
        }

        String accessToken = Jwt.issuer("https://mekano.fiap.com.br/auth")
            .subject(user.getId().toString())
            .upn(user.getName())
            .groups(Set.of(fetchRole(user.getId())))
            .expiresIn(Duration.ofMinutes(15))
            .sign();

        String jti = UUID.randomUUID().toString();
        String refreshToken = Jwt.claims()
            .claim("jti", jti)
            .claim("sub", user.getId().toString())
            .expiresIn(Duration.ofDays(7))
            .sign();

        String tokenHash = passwordHasher.hash(refreshToken);
        refreshTokenRepository.save(new RefreshTokenData(
            jti, tokenHash, user.getId(), LocalDateTime.now().plusDays(7), null));

        return new TokenPair(accessToken, refreshToken);
    }
}
```

## Common Pitfalls

### Pitfall 1: Parallel Developer Integration Chaos
**What goes wrong:** 5 devs work in parallel but their code doesn't integrate on Day 4.
**Why it happens:** Auth dev depends on user_roles table (V6) but Cliente/VOs (V7-V10) don't exist yet. Entities reference Port interfaces that don't exist yet.
**How to avoid:** Wave 1 = Auth walking skeleton (V6 migration, AuthService, AuthResource). Wave 2 = entity CRUDs in parallel. Each entity is self-contained. Domain entities and ports are defined first (shared API contract), infrastructure and REST are parallel.
**Warning signs:** Merge conflicts in `application.properties`, duplicate Jandex plugin configs.

### Pitfall 2: MapStruct with Nested VOs (G3)
**What goes wrong:** Mapper compiles but produces entities with null fields.
**Why it happens:** Wrong annotation processor path order (MapStruct before Lombok) or missing `@Mapper(uses = {CpfMapper.class})` for VO flattening.
**How to avoid:** Verify `annotationProcessorPaths` order: Lombok → lombok-mapstruct-binding → mapstruct-processor. Create helper mappers for each VO (CpfMapper, TelefoneMapper, EnderecoMapper) with `@Named` methods.
**Warning signs:** Entity persists with null fields, NPE at runtime.

### Pitfall 3: OS State Machine — Missing Transitions
**What goes wrong:** OS enters an illegal state due to missing transition validation.
**Why it happens:** `setStatus()` is accidentally called instead of explicit method, or new developer adds transition without updating the matrix.
**How to avoid:** No `setStatus()` — only explicit methods (`iniciarDiagnostico`, `aprovarOrcamento`). `@Version` on OS entity for optimistic locking. Parameterized test that validates ALL origin×destination pairs.
**Warning signs:** Tests that only test valid transitions, never invalid ones.

### Pitfall 4: @RequestScoped on Resources Forgot (G8)
**What goes wrong:** JWT claims injection returns null or stale data.
**Why it happens:** Resource annotated with `@ApplicationScoped` instead of `@RequestScoped`.
**How to avoid:** ALL JAX-RS resources with JWT claim injection MUST be `@RequestScoped`. Code review checklist item.
**Warning signs:** Intermittent claim injection failures.

### Pitfall 5: Refresh Token Race Condition
**What goes wrong:** Two concurrent refresh requests both succeed, both refresh tokens remain valid.
**Why it happens:** No pessimistic locking on refresh token rotation.
**How to avoid:** `@Lock(PESSIMISTIC_WRITE)` on refresh token entity during rotation. Mark token as rotated atomically. Verify token hash matches before rotation.
**Warning signs:** Same refresh token usable multiple times, token replay attacks.

## Security Domain

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | yes | JWT access token (15min) + refresh token rotation with `@Lock(PESSIMISTIC_WRITE)` |
| V3 Session Management | yes | Refresh tokens with rotation. Sessão = JWT stateless. `POST /auth/logout` invalida refresh token. |
| V4 Access Control | yes | `@RolesAllowed` on every resource + method. `groups` claim single role. |
| V5 Input Validation | yes | Bean Validation on DTOs (`@NotBlank`, `@Email`, `@Size`). VO validation in domain constructor (`AppException(400)`). |
| V6 Cryptography | yes | Ed25519/EdDSA for JWT signing. BCrypt for password hashing (existing). |

### Known Threat Patterns for Quarkus+SmallRye JWT

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| JWT algorithm confusion (alg:none) | Tampering | Hard-coded `mp.jwt.verify.publickey.algorithm=EdDSA` — never reads alg from token header |
| Refresh token replay | Elevation of Privilege | Rotation on each use + `@Lock(PESSIMISTIC_WRITE)` + store hash (not token value) |
| Stale JWT after logout | Information Disclosure | Short-lived access tokens (15min) + server-side refresh token invalidation |
| Resource enumeration via sequential IDs | Information Disclosure | Hybrid ID pattern (UUID public, Long internal PK) |
| Password brute force via login endpoint | Tampering | `TokenBucketRateLimiter` on `/auth/login` |
| Session fixation via stolen refresh token | Elevation of Privilege | Rotation generates new refresh token on each use, invalidates old one |

## Open Questions

1. **Does Quarkus 3.36.0 support EdDSA/Ed25519 out of the box via `mp.jwt` config?**
   - What we know: The `mp.jwt.verify.publickey.algorithm` property supports `ES256`, `RS256` as documented values. `EdDSA` is documented in the general JWT spec but not explicitly in Quarkus docs for the MP-JWT config.
   - What's unclear: Whether Quarkus/SmallRye JWT auto-detects EdDSA from the key type or needs explicit `EdDSA` value in the config property. The codebase CLAUDE.md already uses `mp.jwt.verify.publickey.algorithm=EdDSA` as a convention.
   - Recommendation: Test during Wave 1. If EdDSA fails, ES256 is a well-documented alternative (Elliptic Curve).

2. **Does `TokenBucketRateLimiter` already exist on disk?**
   - What we know: Referenced in INTEGRATIONS.md as planned, not found in infrastructure/security/ directory.
   - What's unclear: Is it planned but not yet implemented, or does it exist elsewhere?
   - Recommendation: Implement a simple `@Provider @ApplicationScoped ContainerRequestFilter` if the file doesn't exist. 10 attempts/minute per email.

3. **Do existing `UserEntity` and `User` fields need updating to support the `role` field?**
   - What we know: Roles are in `user_roles` table (N:N). The JWT `groups` claim has single role per user.
   - What's unclear: Does `User` domain entity need a `role` field, or is it always looked up via the `user_roles` join?
   - Recommendation: Add a `findRolesByUserId(UUID)` method to `UserRepositoryPort`. The `AuthService` fetches the role during login.
