# Codebase Concerns

**Analysis Date:** 2025-01-29

---

## ⚠️ Critical: Project Is an Unmodified Scaffold

**The entire application is the default Quarkus project generator output. No real business logic has been written.**

- Issue: The only source file is the generated placeholder `GreetingResource.java`. The project has not yet been developed into its intended purpose.
- Files: `src/main/java/com/fiap/GreetingResource.java`, `src/main/resources/application.properties`
- Impact: Nothing in the codebase reflects actual product requirements. All concerns below describe what is **missing** before the project can be considered a real application.
- Fix approach: Define domain model, add real REST resources, persistence, and security layers before any other development.

## Tech Debt

**No application.properties configuration:**
- Issue: `src/main/resources/application.properties` is completely empty — zero configuration defined.
- Files: `src/main/resources/application.properties`
- Impact: App runs only on Quarkus defaults. No datasource, no port overrides, no profile-specific config, no logging configuration, no security settings.
- Fix approach: Define at minimum `%dev`, `%test`, and `%prod` profiles with appropriate datasource, logging, CORS, and HTTP settings.

**SNAPSHOT version in production path:**
- Issue: `pom.xml` declares `<version>1.0.0-SNAPSHOT</version>`. SNAPSHOT artifacts are mutable and unsuitable for production deployments.
- Files: `pom.xml` line 6
- Impact: CI/CD pipelines may pick up inconsistent artifact versions; deployment traceability is broken.
- Fix approach: Adopt a release versioning strategy (e.g., semver via `maven-release-plugin` or CI-driven tagging) before deploying.

**Integration tests globally disabled:**
- Issue: `<skipITs>true</skipITs>` in `pom.xml` (line 17) skips all `@QuarkusIntegrationTest` tests in the default build lifecycle. They only run in the `native` profile.
- Files: `pom.xml` line 17, `src/test/java/com/fiap/GreetingResourceIT.java`
- Impact: Integration tests never run in standard `mvn verify` or CI pipelines unless the `native` profile is explicitly activated.
- Fix approach: Remove `<skipITs>true</skipITs>` or create a dedicated `integration` Maven profile that enables them on JVM mode as well.

**Legacy JAR Dockerfile retained:**
- Issue: `src/main/docker/Dockerfile.legacy-jar` packages via the deprecated legacy JAR format.
- Files: `src/main/docker/Dockerfile.legacy-jar`
- Impact: Legacy JAR mode has reduced startup optimisation compared to fast-jar; retaining the file creates ambiguity about which Dockerfile to use.
- Fix approach: Remove `Dockerfile.legacy-jar` or add a clear comment marking it as unsupported.

**README is the default Quarkus boilerplate:**
- Issue: `README.md` is the unmodified template generated by `code.quarkus.io`.
- Files: `README.md`
- Impact: No project-specific documentation, no architecture decisions, no setup instructions for new contributors.
- Fix approach: Replace with project-specific README covering purpose, local setup, environment variables, and API overview.

## Security Considerations

**No authentication or authorization:**
- Risk: The application has no security layer whatsoever. Every endpoint (`/hello`) is publicly accessible with no restrictions.
- Files: `src/main/java/com/fiap/GreetingResource.java`
- Current mitigation: None.
- Recommendations: Add `quarkus-smallrye-jwt` or `quarkus-oidc` dependency and annotate resources with `@RolesAllowed`. Define security policies in `application.properties` before adding real endpoints.

**No input validation framework:**
- Risk: No `quarkus-hibernate-validator` (Bean Validation) dependency is present. Future endpoints will have no structured validation.
- Files: `pom.xml`
- Current mitigation: None — no user input exists yet.
- Recommendations: Add `io.quarkus:quarkus-hibernate-validator` and annotate DTOs with `@NotNull`, `@Size`, etc. before writing real endpoints.

**No CORS configuration:**
- Risk: No CORS policy is configured in `application.properties`. The Quarkus default permits all origins in dev mode and has no explicit production CORS policy.
- Files: `src/main/resources/application.properties`
- Current mitigation: None.
- Recommendations: Set `quarkus.http.cors=true`, `quarkus.http.cors.origins=<allowed-list>`, and `quarkus.http.cors.methods=GET,POST,PUT,DELETE` in the production profile.

**OpenAPI/Swagger UI exposed with no access control:**
- Risk: `quarkus-smallrye-openapi` is included as a runtime dependency, which exposes `/q/openapi` and `/q/swagger-ui` by default in all profiles.
- Files: `pom.xml` line 44-46
- Current mitigation: None.
- Recommendations: Disable Swagger UI in production profiles: `quarkus.swagger-ui.always-include=false` and restrict OpenAPI endpoint access via `quarkus.smallrye-openapi.security-scheme`.

**No HTTPS/TLS configuration:**
- Risk: No TLS is configured. The Dockerfiles expose only port 8080 (plain HTTP).
- Files: `src/main/docker/Dockerfile.jvm` line 94, `src/main/docker/Dockerfile.native` line 26
- Current mitigation: None — acceptable only if TLS is terminated at a load balancer.
- Recommendations: Document TLS termination strategy. If needed, add `quarkus.http.ssl-port` and certificate configuration.

## Performance Bottlenecks

**No persistence layer (potential future N+1 risk):**
- Problem: No ORM or database extension is configured. When Hibernate Panache or JDBC is added later, N+1 query patterns are a common introduction point.
- Files: `pom.xml` — missing `quarkus-hibernate-orm-panache` or `quarkus-jdbc-*`
- Cause: Architectural decision not yet made.
- Improvement path: When adding persistence, use `@NamedEntityGraph` or JOIN FETCH queries, and enable `quarkus.hibernate-orm.log.sql=true` in dev profile to catch N+1 during development.

**No caching strategy defined:**
- Problem: No caching extension (`quarkus-cache`) is included.
- Files: `pom.xml`
- Cause: Scaffold project has no business logic requiring caching.
- Improvement path: Add `io.quarkus:quarkus-cache` and annotate service methods with `@CacheResult` for read-heavy operations.

**Reactive vs. blocking decision not made:**
- Problem: The project uses `quarkus-rest` (RESTEasy Reactive) but `GreetingResource` uses a blocking method signature (`String hello()`). Mixing blocking logic in reactive request handlers degrades throughput.
- Files: `src/main/java/com/fiap/GreetingResource.java` line 13, `pom.xml` line 41
- Cause: Scaffold default.
- Improvement path: Either switch to `quarkus-rest-jackson` with `@Blocking` annotation on blocking methods, or use `Uni<T>` return types for non-blocking handlers.

## Fragile Areas

**Single package, no layering:**
- Files: `src/main/java/com/fiap/` — contains only `GreetingResource.java`
- Why fragile: As the application grows, placing all classes in a single flat package will create coupling and make the codebase hard to navigate.
- Safe modification: Establish a package structure (e.g., `com.fiap.resource`, `com.fiap.service`, `com.fiap.domain`, `com.fiap.repository`) before adding new classes.
- Test coverage: No coverage of non-existent layers.

**No exception handling / error mapping:**
- Files: `src/main/java/com/fiap/` — no `ExceptionMapper` classes exist.
- Why fragile: Without a `@Provider`-annotated `ExceptionMapper`, unhandled exceptions will surface as 500 responses with default Quarkus error bodies, leaking stack trace details in some configurations.
- Safe modification: Add a global `ExceptionMapper<Throwable>` and domain-specific mappers (e.g., for `EntityNotFoundException`) before writing resource methods that can throw.

## Missing Critical Features

**No persistence layer:**
- Problem: No database driver, no ORM, no migration tool (Flyway/Liquibase) is configured.
- Blocks: Cannot persist any domain data.
- Recommended additions: `quarkus-hibernate-orm-panache`, a JDBC driver (`quarkus-jdbc-postgresql` or `quarkus-jdbc-h2` for tests), and `quarkus-flyway` for schema migrations.

**No health or readiness probes:**
- Problem: `quarkus-smallrye-health` is absent from `pom.xml`. No `/q/health`, `/q/health/live`, or `/q/health/ready` endpoints are available.
- Blocks: Cannot integrate with Kubernetes liveness/readiness probes or load balancer health checks.
- Recommended fix: Add `io.quarkus:quarkus-smallrye-health` dependency.

**No metrics/observability:**
- Problem: No `quarkus-micrometer` or `quarkus-smallrye-metrics` dependency is present.
- Blocks: No runtime performance data, no Prometheus scraping endpoint.
- Recommended fix: Add `io.quarkus:quarkus-micrometer-registry-prometheus` for production observability.

**No logging configuration:**
- Problem: `application.properties` is empty; no log levels, no log format, no structured JSON logging configured.
- Blocks: Logs are in unstructured human-readable format only; difficult to ingest in log aggregation platforms (ELK, Splunk, Datadog).
- Recommended fix: Set `quarkus.log.console.format`, `quarkus.log.level`, and consider `quarkus-logging-json` extension for production.

**No CI/CD pipeline definition:**
- Problem: No `.github/workflows/`, no `Jenkinsfile`, no `.gitlab-ci.yml` is present.
- Blocks: No automated build, test, or deployment pipeline.
- Recommended fix: Add a GitHub Actions workflow (or equivalent) that runs `mvn verify` and builds the container image on every push.
